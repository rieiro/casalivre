# Calendar-sync schema (BD design, develop @561df1a, SCHEMA 30 -> next)

Scope: backlog.md:64 (Postgres-only calendar sync). Read: schema.pgsql.sql:182-201, HouseRepository.php:409-555, CalendarSync.php,
Acoes/ICalImport.php, Acoes/ICalFeedRemove.php, helpers/ical.php:80-140 (`import_ics`), scripts/sync-calendars.php, views/calendar.php:104.
Lab: PG 18.6 scratch (port 55250), develop schema + migrate + synthetic load: 142,624 properties, 5,000 users (250 set inactive);
calendar_feeds tested at 200k (201,296 feeds, 41,224 on inactive accounts) and at 30k (4,396 on inactive accounts).
calendar_days has 10.95M rows (30k properties x 365 nights): 20.0% blocked, of those 63% reserva, 13% sync and 24% sistema.
Times are medians of runs 2-6 inside BEGIN/ROLLBACK. The box was shared with another load, so treat +-20% as noise. Logs are in design/log/.
**M** = measured here. **E** = estimate/arithmetic.

## Decisions (and where I changed the proposal)
- a) Kept as proposed: `slot` + UNIQUE (property_id, slot), the three new columns, and a **plain** `idx_feeds_due (next_sync_at)`.
  A partial index `WHERE next_sync_at < 'infinity'` is **not used** by the claim, because the planner cannot prove `next_sync_at <= now()` implies it
  (now() is not immutable). The result is a Seq Scan at 9.5 ms vs 0.46 ms with the plain index (M, 30k feeds, 6k stopped).
  Stopped rows sort last, so the plain index never visits them.
- b) Kept: stopped = `next_sync_at = 'infinity'`. The 16th consecutive failure stops the feed, **73.5 h (~3 days) after the first failure** (M, table below).
- c) **Changed:** claim the oldest due row whatever its account state. One UPDATE gives it a 10-min lease if the account is active, else +1 day, and returns `active`.
  The worker skips `active = false`. The proposed "active-only" claim walks every due inactive feed on every claim:
  | due inactive feeds (200k table) | 41,224 | 10,000 | 1,000 | 0 |
  |---|---|---|---|---|
  | active-only claim (M) | 113 ms / 124.6k buf | 47 ms / 50.8k | 8.0 ms / 6.0k | 0.38 ms |
  | claim-any + CASE (M) | 1.4 ms / 52 buf | 0.60 ms | 0.44 ms | 0.46 ms |
  At 30k feeds (4,396 inactive due): 15.9 ms vs 0.94 ms; nothing due: 0.45 ms both (M). An inactive feed costs one claim per day
  (E: 41k/day = 0.5/s); after reactivation it waits up to 1 day (the owner's retry button sets now()).
- d) Kept, except that `fail_count = fail_count + 1` replaces `LEAST(fail_count+1, 20)`: the feed stops at 16, so the cap is dead code.
  `interval * power(2,n)` is exact (powers of two) and returns interval (M).
- e) Kept: `feed_id` with no FK and no new index. **Changed: the import is a diff, not "free all then re-insert".**
  Nights still in the feed are not touched, so an unchanged sync writes nothing (M: 0 WAL vs 22.8 kB for the naive replace).
  Rule: **the first holder keeps the night**: an owner block (`sistema`) or another feed's night is never taken.
  Today `import_ics` re-tags owner `sistema` nights as sync/reserva, and `releaseImported` later unblocks them. This design removes that.
- f) Kept: one INSERT ... SELECT picks the lowest free slot. It uses `ON CONFLICT DO NOTHING` (no error) plus an app retry of at most 5 attempts.

## DDL (schema.pgsql.sql; seeds insert no feeds; tests/standalone/sync_calendars_activity_test.php:12 must pass `slot`)
```sql
CREATE TABLE IF NOT EXISTS calendar_feeds (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    property_id INTEGER NOT NULL REFERENCES properties(id) ON DELETE CASCADE,
    slot SMALLINT NOT NULL CHECK (slot BETWEEN 1 AND 5),   -- 5-feed limit in the DB
    url TEXT NOT NULL,
    title TEXT NOT NULL DEFAULT '',
    last_status TEXT,                                      -- OK / NOK / PENDENTE (views/calendar.php:104 unchanged)
    last_synced_at TIMESTAMP,                              -- last attempt, as today
    next_sync_at TIMESTAMPTZ NOT NULL DEFAULT now(),       -- 'infinity' = stopped
    fail_count SMALLINT NOT NULL DEFAULT 0,
    last_error TEXT CHECK (last_error IN ('bad_url','private_ip','http_4xx','not_ics','too_big','timeout','dns','http_5xx')),
    UNIQUE (property_id, url),
    UNIQUE (property_id, slot)
);
CREATE INDEX IF NOT EXISTS idx_feeds_due ON calendar_feeds (next_sync_at);
-- calendar_days: add one column, no FK, no index (index count public 58 -> 60: +UNIQUE slot, +idx_feeds_due)
    feed_id INTEGER,          -- feed that blocked the night (origin sync/reserva); NULL for owner/empty rows
```

## SQL
Claim (one statement; $active is false means: skip the fetch, already pushed +1 day):
```sql
UPDATE calendar_feeds f SET next_sync_at = now() + CASE WHEN c.active THEN interval '10 minutes' ELSE interval '1 day' END
FROM (SELECT f2.id, (p.status = 'active' AND u.status = 'active') AS active
      FROM calendar_feeds f2 JOIN properties p ON p.id = f2.property_id JOIN users u ON u.id = p.user_id
      WHERE f2.next_sync_at <= now() ORDER BY f2.next_sync_at LIMIT 1 FOR UPDATE OF f2 SKIP LOCKED) c
WHERE f.id = c.id RETURNING f.id, f.property_id, f.url, c.active;
```
Import, after the HTTP fetch and outside any earlier transaction. $nights/$origins are the feed's nights from today to `max_calendar_day`;
the app drops CANCELLED events and our own UID. All of it is one transaction:
```sql
SELECT pg_advisory_xact_lock(48001403, :property_id);         -- two-int form; does not collide with ListingSearch's bigint lock
SELECT 1 FROM calendar_feeds WHERE id = :feed AND property_id = :property_id FOR KEY SHARE;  -- 0 rows: feed removed, ROLLBACK
UPDATE calendar_days SET blocked = 0, origin = '', feed_id = NULL           -- free nights the feed dropped (keeps price/min_nights)
 WHERE property_id = :property_id AND feed_id = :feed AND day >= :today AND day <> ALL (:nights::date[]);
INSERT INTO calendar_days AS c (property_id, day, blocked, origin, feed_id)
SELECT :property_id, n.day, 1, n.origin, :feed FROM unnest(:nights::date[], :origins::text[]) AS n(day, origin)
LEFT JOIN calendar_days o ON o.property_id = :property_id AND o.day = n.day
WHERE o.day IS NULL OR o.blocked = 0 OR (o.feed_id = :feed AND o.origin <> n.origin)   -- prefilter: unchanged nights write nothing
ON CONFLICT (property_id, day) DO UPDATE SET blocked = 1, origin = EXCLUDED.origin, feed_id = EXCLUDED.feed_id
 WHERE c.blocked = 0 OR (c.feed_id = EXCLUDED.feed_id AND c.origin <> EXCLUDED.origin);  -- recheck (owner edits take no lock)
-- only if the UPDATE above freed rows: let the other feeds re-claim those nights now
UPDATE calendar_feeds SET next_sync_at = now() WHERE property_id = :property_id AND id <> :feed AND next_sync_at > now() AND next_sync_at < 'infinity';
UPDATE calendar_feeds SET next_sync_at = now() + interval '30 minutes', fail_count = 0, last_error = NULL,
       last_status = 'OK', last_synced_at = :now WHERE id = :feed;
```
Fetch failure (no calendar_days writes):
```sql
-- temporary (timeout, dns, http_5xx)
UPDATE calendar_feeds SET fail_count = fail_count + 1, last_error = :code, last_status = 'NOK', last_synced_at = :now,
       next_sync_at = CASE WHEN fail_count + 1 >= 16 THEN 'infinity'
                           ELSE now() + interval '30 minutes' * LEAST(power(2, fail_count), 12) END WHERE id = :feed;
-- permanent (bad_url, private_ip, http_4xx, not_ics, too_big)
UPDATE calendar_feeds SET fail_count = fail_count + 1, last_error = :code, last_status = 'NOK', last_synced_at = :now,
       next_sync_at = 'infinity' WHERE id = :feed;
```
| fail_count before | 0 | 1 | 2 | 3 | 4..14 | 15 |
|---|---|---|---|---|---|---|
| next delay (M) | 30m | 1h | 2h | 4h | 6h each | infinity (stopped) |
| cumulative (M) | 0.5h | 1.5h | 3.5h | 7.5h | 13.5h .. 73.5h | stops at 73.5 h |

Feed removal replaces `releaseImported` and the synchronous `resyncProperty`. It runs in one transaction under the same advisory lock:
```sql
DELETE FROM calendar_feeds WHERE id = :feed AND property_id = :property_id RETURNING id, url, title;
UPDATE calendar_days SET blocked = 0, origin = '', feed_id = NULL WHERE property_id = :property_id AND feed_id = :feed
RETURNING day, blocked, price, min_nights, origin;            -- nightAudit; rows stay (as releaseImported today, no DELETE)
UPDATE calendar_feeds SET next_sync_at = now() WHERE property_id = :property_id AND next_sync_at > now() AND next_sync_at < 'infinity';
```
Add a feed. The current pre-checks stay for the 'duplicate'/'limit' messages. 0 rows with count < 5 and no such url means a lost slot race, so retry (at most 5):
```sql
INSERT INTO calendar_feeds (property_id, slot, url, title)
SELECT :property_id, s.slot, :url, :title
FROM (SELECT min(g)::smallint AS slot FROM generate_series(1, 5) g
      WHERE NOT EXISTS (SELECT 1 FROM calendar_feeds f WHERE f.property_id = :property_id AND f.slot = g)) s
WHERE s.slot IS NOT NULL
ON CONFLICT DO NOTHING RETURNING id, url, title;
```
UI and worker helpers:
```sql
-- markFeedPending (owner re-save / retry button / manual resync):
UPDATE calendar_feeds SET next_sync_at = now(), fail_count = 0, last_error = NULL, last_status = 'PENDENTE' WHERE id = :feed AND property_id = :property_id;
-- owner list (feeds()): UNIQUE (property_id, slot) serves it
SELECT id, property_id, title, url, last_status, last_synced_at, last_error, fail_count, next_sync_at = 'infinity' AS stopped
FROM calendar_feeds WHERE property_id = :property_id ORDER BY id;
```

## Evidence (M)
- Concurrency: pgbench, 8 clients, 60 s, 200k feeds all due, every claim logged in the same statement:
  claim-any = 129,278 claims, **2,155 claims/s**, 3.7 ms avg latency, **0 duplicate ids**, 0 failed transactions.
  The active-only claim reached 448 claims/s at 17.9 ms (walks the inactive rows), with 0 duplicates.
  Needed rate (E): 30k feeds every 30 min is 17 claims/s.
- Lease: a committed claim leaves the row invisible to other claims for 10 min (re-claim returned 0 rows; remaining lease 9:59.8).
  After shifting `next_sync_at` back by 10 min the next claim returned it. A claim transaction killed with
  `pg_terminate_backend` was re-claimable immediately, while SKIP LOCKED had skipped it during the open transaction.
- Import on a property with 63 feed nights (PK range scan of 365 rows; no feed_id index needed):
  | statement set | ms | WAL |
  |---|---|---|
  | diff + prefilter, unchanged feed | 0.37 | 0 B |
  | diff, 3 nights cancelled + 3 new | 0.64 | 1.4 kB |
  | without prefilter (ON CONFLICT only), unchanged | 1.04 | 3.4 kB (63 row locks) |
  | naive free-all + re-insert | 5.1 | 22.8 kB |
  | feed removal (63 nights) | 0.76 | 13.4 kB |
  WAL per day (E) at 30k feeds x 48 syncs = 1.44M syncs: naive ~33 GB, ON CONFLICT-only ~4.9 GB, diff only on changes.
- feed_id width on 10.95M rows: after the UPDATE plus CLUSTER the heap is still 541,851,648 B (identical) and the PK is 245,981,184 B.
  Average tuple size went from 40.3 to 40.9 B; MAXALIGN padding absorbs the 4 bytes.
  The search NOT EXISTS probe is unchanged: city dates p1 0.57 -> 0.60 ms, total 0.82 -> 0.49 ms, SP 20 km 27.2 -> 28.1 ms (sort-bound).
- Slot insert, 10 concurrent sessions per property, each holding its transaction 0.3 s: single attempt gives 1 success and 9 x 0 rows (no error);
  with at most 5 retries, 30/30 rounds ended with exactly 5 rows (slots 1-5), 0 errors, 0 deadlocks (pg.log); losers end on the 'limit' check.

## Two feeds, same night
The PK allows one row. The first holder keeps it (the INSERT only takes `blocked = 0` rows) and its `feed_id` stays.
When that feed frees the night (cancellation or feed removal), the freeing transaction sets `next_sync_at = now()` on the property's other feeds.
The night is then free only until a worker re-claims one of those feeds. Worst case (E): the claim latency (seconds), or the other feed's backoff (up to 6 h) if it is failing.
It never comes back if that feed is stopped. An owner `sistema` block is never taken by a feed, which differs from today.
If the owner unblocks a night a feed also has, the night stays free until that feed's next sync (<= 30 min). Optional: call markFeedPending for the property's feeds on owner unblock.

## Risks / Followups
- No FK on feed_id: correctness relies on the advisory lock + the `FOR KEY SHARE` check in the import, and on removal using the same lock.
- A slow worker (fetch takes longer than the 10-min lease; fetch timeout is 20 s) can import twice. That is harmless: the import is idempotent and the lock serializes it.
- `calendar_feeds` gets 2 non-HOT updates per sync (claim + finish), ~33/s at 30k (E). Default autovacuum is enough at 30k rows.
- Rows freed by removal/cancellation stay as empty rows, as `releaseImported` does today (3.8M empty rows in this synthetic set).
  Deleting empty rows is a separate decision (`clearBlockedAfter` already deletes past the horizon).
