## 1. Calendar-sync (calendar-sync.md)
- calendar_feeds: `slot` 1-5 + `UNIQUE (property_id, slot)` (5-feed limit in the DB, no trigger), `next_sync_at`, `fail_count`, `last_error`, plain `idx_feeds_due`. calendar_days: `feed_id` (no FK, no index; same table size).
- Claim: one UPDATE takes the oldest due feed of any account; lease 10 min if active, +1 day if not (worker skips). 0.4-1.4 ms at 200k feeds; the active-only claim degrades to 113 ms [M]. 8 clients: 2,155 claims/s, 0 duplicates.
- Import is a diff under `pg_advisory_xact_lock(48001403, property_id)`: unchanged sync = 0 rows, 0 B WAL, 0.37 ms [M]; naive replace 22.8 kB. Rule: the first holder keeps the night (an owner block is never taken by a feed; differs from today's `import_ics`).
- Backoff 30m, 1h, 2h, 4h, then 6h; stops on the 16th failure (73.5 h). Stopped = `next_sync_at = 'infinity'`. Re-save resets.
- Decisions for Produto/Gerente, decided (Produto, 2026-11-03): Calendar-sync stops after 16 consecutive failures (about 3 days, 73.5 h), replacing 72 h. Owner unblock does not mark feeds pending (a 1-day lease for inactive accounts and re-save resets are enough for the pilot). PR5 map: dates filter before the top-300 pick (probe up to 5,000 loops); pins never show unavailable listings; bubble counts stay approximate (~N) per [spec-busca-ordenacao-filtros](../../produto/specs/spec-busca-ordenacao-filtros.md) §7.4.

# BD answers to the [BD?] points in adr001-pr5-pr6-calendar-budgets.md
Tags: [M] measured earlier (source), [C] checked in code on develop, [E] estimate to be measured at the PR's review, numbers are in calendar-sync.md / search-followup-242.md (same folder).

1. **idx_prop_nb_active and the cap of 6: not counted.** ADR §12.6 lists the six explicitly (ls place_rank, ls place_rating, ls geo, channel_rank PK, idx_chrank_place, avail_runs PK) and says back-office indexes are outside. idx_prop_nb_active is a properties-side filter index (neighborhood listing filter) and is not in that list. Confirmed after PR4c: idx_prop_place_active and idx_prop_latlng_active are dropped, so properties holds 1 search-adjacent partial index. Honest caveat: if Rafael meant "every index a search query reads", the count is 7. §12.6 names idx_prop_nb_active as outside the cap. PR5 and PR6 add 0 indexes: agreed.
2. **calendar_feeds claim index: one plain btree on (next_sync_at), back-office, outside the 6.** Stopped feeds use next_sync_at = 'infinity', so they never match `<= now()`; no extra column. Claim shape: `UPDATE ... WHERE id = (SELECT ... ORDER BY next_sync_at LIMIT 1 FOR UPDATE OF f SKIP LOCKED) RETURNING`. To keep the claim at <= 2 ms the inactive-account check must not sit inside the walk: claim the row regardless and push feeds of inactive accounts to now() + 1 day in the same UPDATE (worker skips them). A partial index `WHERE next_sync_at < 'infinity'` is NOT used (now() is not immutable): seq scan 9.5 ms vs 0.46 ms [M], so plain. Claim 0.4-1.4 ms at 200k feeds, 2,155 claims/s with 8 clients and 0 duplicates [M]; needed rate is 17-25/s.
3. **Advisory-lock scope: per property, two-int form, sync vs sync is mandatory; booking/hold/host writes do not need it.** Today those writes take no advisory lock [C] and `applyRange` already refuses to touch origin 'sync' or 'reserva' nights. If the sync SQL only writes nights it owns (origin 'sync', same feed_id) or unblocked rows, row locks on calendar_days_pkey are enough and a booking never waits on a sync. The lock is needed because two feeds of one property can sync in parallel and both replace rows. One lock per transaction, always taken first: no deadlock. If Arquitetura still wants bookings to take it, the wait is bounded by the sync tx p99, but it means touching booking code for no data-integrity gain. Final SQL: `pg_advisory_xact_lock(48001403, property_id)` first, then a `FOR KEY SHARE` check that the feed still exists (no FK on feed_id), then the diff. Owner/booking nights are never taken by a feed (first holder keeps the night). See calendar-sync.md.
4. **PR6 keyset predicate form.** Mixed direction is solved with a negated id in a row comparison: `(sort_value, -s.id) > (?, ?)` (price ASC, id DESC), integer ids only. Place it in the OUTER query after total_price is computed by the LATERAL, not in the capped CTE: the CTE must stay the full candidate set so the 2,001 / 5,001 cap and the count do not change between pages. Each page re-sorts the <= 2,000/5,000 candidates in memory (as Arquitetura assumed). For nightly_price (a column in INCLUDE) the same outer form works. Rows without a price must be excluded or sorted by a NULL rule written in the spec, since NULL breaks row comparison. Plan check at PR6 review.
5. **Map availability probe loops.** Produto (2026-11-03): dates filter before the top-300 pick, so the probe runs up to 5,000 loops and pins never show unavailable listings. Bubble counts stay approximate (~N) per [spec-busca-ordenacao-filtros](../../produto/specs/spec-busca-ordenacao-filtros.md) §7.4. [M] #242 bbox + dates at SP 20 km: 15-28 ms. The DB budget of <= 40 ms holds for that case at 44k candidates [M] (not under load).
6. **Map DB budget <= 40 ms p95 under load, IOS idx_ls_geo, Heap Fetches 0 when vacuumed:** plausible [M: G-2 guard 2.7-8.5 ms; bbox 12-23 ms single]. Buffers <= 1,500 at the cap and Rows Removed <= 60k at 8 deg are [E]; I will measure both when PR5 arrives and will not pre-approve them.
7. **Index sizes after widening (geo <= 32 MB, place <= 10 MB):** [M] 16 / 3.9 MB at PR4b; adding two int4 columns is about +8 bytes per entry, so [M after the #242 follow-up design] with rating_tenths in INCLUDE: place indexes 4.07 -> 5.58 MB, geo 16.39 -> 16.79 MB at 142k, so PR6's two extra columns should stay inside <= 10 / <= 32 MB [E]. Write cost <= 2.0 ms median: [M] 1.21-1.32 ms at PR4b; INCLUDE columns only cost when their value changes. [E] <= 1.6 ms, measured at PR6.
8. **Calendar statements and writes per sync.** <= 6 statements is feasible: lock; free this feed's nights no longer in the feed; one INSERT ... SELECT unnest(...) WHERE NOT EXISTS (already blocked) ON CONFLICT DO UPDATE ... WHERE blocked = 0; update the feed row. A no-op sync then writes 0 calendar_days rows because the anti-join runs before ON CONFLICT (ON CONFLICT DO UPDATE ... WHERE false still locks the row, #238). Statements are 6: lock, feed-exists check, free dropped nights, insert diff, re-due other feeds (only if rows freed), finish. [M] unchanged sync 0.37 ms and 0 B WAL; 3 nights cancelled + 3 new 0.64 ms, 1.4 kB; full removal of 63 nights 0.76 ms, 13.4 kB. Full 366-night insert not measured separately; the budget of <= 200 kB is [E] plausible.
9. **72 h stop rule.** I model it with fail_count, not time, to avoid another column: the feed stops on the 16th consecutive failure, 73.5 h after the first [M table in calendar-sync.md]. Produto (2026-11-03) confirmed that stop (about 3 days, 73.5 h), replacing 72 h. Jitter 0-300 s: agreed. Claim rate: 45k feeds / 1800 s = 25 claims/s, trivial for the DB (measured capacity 2,155/s); the worker count is bound by fetch time, not by the DB.
